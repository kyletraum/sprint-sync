## Closed, with how it was verified

### M1 — liveness probe killed the container ~65s into a 153s startup window

`infra/api/api-containerapp.module.bicep:61-71` now emits a `Startup` probe on
`/alive`: `initialDelaySeconds: 10`, `periodSeconds: 10`, `failureThreshold: 30`
— **300s** to the 30th consecutive failure, against the 65s that was killing it.
While a startup probe is failing within its threshold, ACA runs neither liveness
nor readiness, so the liveness budget no longer applies during migration.

*Verified*: read the **generated** bicep, not the AppHost source — the probe has
to survive `azd infra gen` to matter. `infra-drift` passes.

*Honest limit, recorded in the AppHost comment*: 300s is **not** derived from the
pre-listen window, which is a **sum** (container start + serverless resume + up
to 180s on `sp_getapplock` + 60s-per-command DDL + seeding), replayed from zero
by the EF execution strategy on any transient fault. 300s dominates the largest
single term, not the sum. `failureThreshold` is capped at 30 by the ARM
validator, so the window can only widen through `periodSeconds`. **T041 must
re-check this against a real cold start under cross-revision contention.**

### M2 — the CORS allow-list had no durable configuration path

Wired end to end: `AppHost.cs:101` declares the parameter, `:122` binds
`Cors__AllowedOrigins__0`, `infra/main.bicep:19` takes it, and
`infra/main.parameters.json:20-21` maps it to `AZURE_CORS_ALLOWED_ORIGINS`. The
docs now say `azd env set … && azd deploy api` rather than an out-of-band edit
that the next `azd deploy` would silently revert.

*Verified*: traced the whole chain including the generated files.

### B-1 (round 3) — the M2 fix broke the local run loop

`AddParameter("CorsAllowedOrigins")` had no seed in
`src/SprintSync.AppHost/appsettings.json`. Aspire resolves parameter values
eagerly in run mode, so the missing key threw `MissingParameterValueException`,
which surfaced as `dotnet run --project src/SprintSync.AppHost` **hanging** with
no API and no error naming the parameter, because `WaitFor(api)` then blocked the
SPA too. Publish mode never resolves values, so `azd infra gen`, `dotnet build`
and the entire test suite stayed green while the documented local loop was dead.

Seed added, with a comment stating the rule for every future `AddParameter`.

### M3 — `continueOnError: true` swallowed a failed Static Web App provision

`azure.yaml` postprovision now carries **no** `continueOnError`; the posix branch
opens `set -eu` and the pwsh branch sets `$ErrorActionPreference = 'Stop'` with
explicit `$LASTEXITCODE` checks — needed because `az` is a native executable and
its failures do not surface as terminating errors.

Optionality is now expressed **per command**: the budget backstop may fail with a
loud warning, the SWA deployment may not. An empty hostname is caught explicitly
and exits 1, so the trailing `echo` can no longer become the hook's exit status.

*Verified*: read both branches of the hook in full.

### M4 + B-3 — the workload-profile rule was dead on the enforcing twin

M4 fixed the whole-file negative arm that let one `Consumption` entry immunise
every sibling in a `workloadProfiles` array.

**B-3 then found the twins still disagreed, in both directions.**
`check-idle-cost.sh` was case-sensitive on the property name, but bicep binds
properties case-insensitively — so ARM accepts `workloadprofiletype: 'D4'` and
deploys a real billable node that the *enforcing* twin never saw. The `.ps1`
lookahead meanwhile accepted `ConsumptionPlus`, and named no profile in its
failure message. Both now extract the value and compare it to exactly
`Consumption`, case-insensitively.

*Verified*: fixture suite **21/21** locally and in CI, including the new
`mixed-workload-profiles` case, with **7 twin-parity assertions and no skips** —
so pwsh was present on the runner and both twins actually executed. The guard
exits 0 against the real tree. FR-012 parity is now machine-checked on the path
CI enforces, having been false as recently as round 1.

### S6 — `/ready` was missing from the OpenTelemetry trace filter

Added in `src/SprintSync.ServiceDefaults/Extensions.cs`. It was the worst of the
three to miss: readiness polls at `periodSeconds: 5` against liveness at 30, so
it is **six times the span volume of the probe that was already excluded** —
~720 spans/hour per warm replica, all shipped by `UseAzureMonitor()`.

**And it is tested** — `tests/SprintSync.Api.Tests/Contract/ProbeTracingTests.cs`.
The failure mode is silent and billable, which is the same argument that
justifies the idle-cost guard, so the rule gets a test rather than a comment.

*Verified by mutation*: removing the `/ready` clause makes the test fail with
`Collection: ["/api/v1/me", "/ready"]` — positive control traced, `/alive` and
`/health` excluded, `/ready` present only when the fix is gone. Fix restored,
suite 67/67.

Two deliberate design choices, each one a way the test could have been worthless:

- **In-memory exporter, not an `ActivityListener`.** The filter does not stop an
  Activity being *created* — ASP.NET Core still creates one — only sampled and
  exported. A listener would see the probe activities and fail for the wrong
  reason. What reaches an exporter is also exactly what `UseAzureMonitor()`
  ships, which is the property under test.
- **A positive control, asserted first.** Without it the test passes when the
  pipeline exports nothing at all, and the exclusion assertions go vacuous —
  which is exactly the S4 defect, still open below.

### N6 — the new public origin served no security headers

`web/sprint-sync-web/public/staticwebapp.config.json` adds
`frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff` and a referrer
policy.

*Verified*: built the SPA and confirmed the file lands at
`dist/staticwebapp.config.json`; `dist` **is** `app_location` in
`deploy-web.yml:80`, and `allowConfigFileUpdates: true` is already set in
`infra-web/staticwebapp.bicep:53`.

*Deliberately partial.* The review split N6 into an unconditional framing half
and a conditional CSP half; **only the framing half is done.**

No `script-src`, `connect-src` or `frame-src`: the SPA authenticates with MSAL,
whose silent token renewal frames the authority, so a policy omitting that origin
breaks sign-in. Those origins are build-time values (`VITE_ENTRA_AUTHORITY`,
`VITE_API_BASE_URL`) that do not exist until T003/T005/T019 and cannot be
interpolated into static JSON. A guessed CSP would trade a real clickjacking fix
for a probable auth outage. **Revisit at T020, once the origins exist.**

No `navigationFallback` either: there is no client-side router, so it would
silently turn 404s into a 200 app shell — asserting a routing model that does not
exist.
