## Context

Feature 002 (Azure Deployment & Operability Baseline) was taken through the full
SpecKit flow in one session: spec → plan → tasks, plus a constitution amendment
that two of its stories exist to implement. **Nothing is implemented. No Azure
resource has been created. Nothing has been spent.**

The feature exists because feature 001's Phase 9B was not really a checklist —
it required standing up an Entra External ID tenant that nothing owned, and that
hard-blocks `azd up` through the preprovision guard. Rather than let deploy work
accumulate as trailing tasks on an application feature, it was migrated whole.

`tasks.md` holds **60 tasks**, and a large, fully unblocked, zero-cost batch is
ready to start immediately. The next session should be able to work for a long
time before anything costs money.

## Local-only state the repository does NOT carry

**This is the part a fresh clone or a different machine cannot reconstruct.**

- `.azure/` is gitignored (azd writes its own `.gitignore`). The azd environment
  `sprintsync-dev` — its name, location, and subscription binding — exists only
  on the machine that ran this session.
- The four `AZURE_AZURE_AD_*` values (once T006 sets them) and
  `BUDGET_ALERT_EMAILS` live in `.azure/<env>/.env`, never committed.
- `az` / `azd` credentials are local.

**Consequence**: any session without those credentials can still do the entire
zero-cost batch below, and will hit a hard wall at T010. Recreate the azd
environment with `azd env new` (T002) before attempting anything marked 💸.

## Decisions already made (do not re-litigate)

- **`infra/api/api-containerapp.module.bicep` is NOT orphaned.** It is azd's
  per-service deploy-time module: regenerated byte-identical, deliberately absent
  from `main.bicep` because it takes `api_containerimage`, which cannot exist at
  provision time. `main.bicep`'s seven outputs are exactly its remaining inputs.
  **Neither wire it in nor delete it.** The 001 handoff's "orphaned module"
  premise (item 1 / old T055) was **disproved**.
- `infra/budget.bicep` is likewise unreachable from `main.bicep` **by design** —
  deployed by the `azure.yaml` postprovision hook.
- Therefore **three legitimate deploy paths** exist. "Unreachable from
  `main.bicep`" is not by itself a defect; "on none of the three" is. An earlier
  draft of the constitution amendment got this wrong and was corrected mid-PR.
- `main.bicep`'s four unused `AzureAd*` parameters are azd-generated and
  reproduce on regeneration. **Do not "fix" them** — identity reaches the API at
  deploy time, not through provisioning.
- `check-azuread-config.{sh,ps1}` already check the correct `AZURE_AZURE_AD_*`
  names. That wiring is sound.
- **Readiness must be database-free.** A DB connectivity check would keep the
  free-serverless database awake against its 60s auto-pause — a silent, continuous
  cost breach. Resolved with an in-memory startup gate.
- **Probes wire through `PublishAsAzureContainerApp`**, not
  `ConfigureInfrastructure`. The 001 handoff and 002's own spec text both name the
  wrong extension point.
- **Web hosting is in scope** (user decision, 2026-08-22) so SC-001 is met
  literally. It deploys from a new `infra-web/` via the declared-hook path — not
  inside generated `infra/`, and not as an azd service.
